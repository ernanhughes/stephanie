# Stephanie Next — Target Architecture

**Status:** STN00 proposal; STN01 database/runtime and STN02 secure chat foundations implemented. Pi/OpenCode adapters and generic execution/run contracts remain unimplemented.  
**Design rule:** evolve existing Stephanie foundations; do not create a parallel chat store, memory system, configuration framework or event bus.

## Ownership

| Owner | Authority |
|---|---|
| Stephanie | Conversation policy, goal interpretation, orchestration, memory/experience, evaluation and learning |
| Hydra / OmegaConf | Configuration composition, reproducible pipelines, per-run overrides |
| SIS | Authenticated local user interaction, visibility, approvals and controls |
| ChatStore | Canonical conversation/message/turn persistence, idempotent turn completion and imported history |
| ServiceContainer | Configured access to Stephanie services; repaired, not replaced |
| Supervisor | Existing Hydra pipeline lifecycle |
| PlanTrace | Pipeline reasoning/evidence trace; extend with references, not replace |
| MemCube / CaseBooks / existing stores | Long-lived structured knowledge and reusable experience |
| Pi | Its own agent loop, sessions, tools and runtime state |
| OpenCode | Its own server/session, model selection, tools and permission behavior |

## Logical flow

```text
SIS conversation
    ├─ Chat mode ─────── ConversationExecutionService → existing LLMService → ChatStore
    ├─ Workflow mode ─── Hydra WorkflowInvoker → existing Supervisor → PlanTrace
    ├─ Code mode ─────── Runtime adapter → Pi RPC OR OpenCode HTTP/SDK
    └─ Research mode ─── allowlisted Hydra research pipeline

ExecutionRun / bounded events ── links conversation, runtime/model, status, evidence
             │
             ├── ChatStore (user-visible messages and conversation identity)
             ├── PlanTrace (pipeline evidence; external run link in metadata/ID)
             └── existing experiment/metric/evaluation and knowledge stores

Experience proposal → independent evaluation → explicit approval → versioned artifact
```

Simple chat must not start a Supervisor pipeline. Existing pipelines must remain runnable without SIS. The bus is not needed for the synchronous first chat path; use the current in-process request/response flow until long-running tasks require persistence and notifications.

## Narrow contracts to add only when their milestone starts

1. **Conversation execution:** `create_conversation`, `send_turn`, `history_window`; canonical store remains `ChatStore`. Keep a stable conversation ID; do not include whole history in context.
2. **Agent runtime:** `capabilities()`, `start(task)`, `send(session, input)`, `events(session)`, `cancel(session)`, `close(session)`. Version the adapter contract; expose runtime/provider/model/version, cwd, allowlist and timeout explicitly.
3. **Structured event:** version, run ID, sequence, timestamp, kind, bounded/redacted payload, provenance. Events are not a second chat transcript.
4. **Workflow invocation:** allowlisted Hydra pipeline identifier + validated overrides → Supervisor result and run ID. Hydra remains the configuration authority.
5. **Evidence:** stable references to chat messages, PlanTrace, tool/run artifacts, tests and evaluator outputs. Preserve provenance; do not label model assertions verified facts.
6. **Improvement proposal/evaluation:** candidate artifact and parent version are separate from evaluator protocol/results. The proposer cannot set final scoring rules or held-out data.

The first slice deliberately uses the existing LLM service and has not introduced generic runtime/event interfaces prematurely.

## Persistence boundary

- Existing `chat_conversations`, `chat_messages`, and `chat_turns` remain authoritative for chat and retain all legacy identifiers.
- The first slice stores model/runtime provenance in assistant-message `meta`, uses existing `provider`, and creates turns with existing relationships. No schema migration.
- Before Pi/OpenCode jobs, add an **additive**, versioned run record related to `chat_conversations` and bounded run-event/evidence references. A run is not a conversation; one conversation can own many runs. Reuse PlanTrace for workflow evidence, not as a generic run table.
- Preserve imported conversation origin/external ID. Do not claim imported messages were generated by a live agent.
- Keep long-term verified knowledge in the existing knowledge/CaseBook/MemCube stores, not in every prompt or raw chat transcript.

## Context, permissions and safety

- Context assembly admits a configured count and character budget; filter roles explicitly. Retrieved/user/web/tool content remains untrusted data.
- Chat has no arbitrary tool access in STN02. Pi/OpenCode retain their native loop and permission rules; Stephanie must not auto-approve their denials.
- Runtime working directory must be explicitly allowlisted; code changes require a bounded workspace and inspectable diff. External side effects require action-specific approval.
- `python -m sis` binds `127.0.0.1` by default. A single local account, server-side session, CSRF and exact Host/Origin checks protect every mounted application route. Remote HTTP is rejected; remote HTTPS requires explicit allowlists.
- Never log provider keys, full credentials, or unbounded prompt/tool output.

## Runtime choices

### Pi

Local Pi `1.2.0` advertises `--mode rpc`. The documented RPC mode is a long-lived child process with JSONL commands, correlated responses, session events, and explicit settle/close semantics. Prefer it over terminal scraping; process supervision must handle Windows pipes, child exit, stderr, timeout, and cancellation. Pin/test a version and pass cwd/model/tools as task-scoped options. Do not mutate global Pi configuration.

### OpenCode

Local OpenCode is `v2.0.29`; its CLI exposes `serve` and `api`. The official server provides an OpenAPI endpoint, session/message APIs, abort, permission responses and SSE events; the JS SDK is generated from that API. Prefer the HTTP server/API or SDK to terminal parsing. Bind to loopback, configure its documented server authentication if the service is reachable beyond a trusted process, and let OpenCode enforce its own tool policy.

Pi and OpenCode are optional and independent. Missing runtime is a clear unavailable result, never silent fallback to another engine.

## Current blockers and choices

1. **Database authority is aligned for the application runtime:** MemoryTool ORM and direct connections now derive from Hydra `db`; STN01 verified `co`, leaving `verity` untouched. Assert database identity before future migrations.
2. **Supervisor/container compatibility is repaired:** one controlled configured pipeline ran and persisted a PlanTrace. Full model-backed workflows remain unverified.
3. **SIS operations:** access-control implementation is tested, but `SIS_AUTH_USERNAME`, password verifier and session secret are not configured in the current environment. Keep the feature off until an operator provisions the local account and readiness gates.
4. **LLM availability:** Ollama `qwen3` has passed a real bounded LLMService call and authenticated SIS turn. `model_verified` remains an explicit operator assertion, not an automatic health guess.
5. **No migration chain:** establish an additive migration mechanism before adding run tables. The `create_all` utility requires explicit local/test opt-in and is not a migration system.

## Request lifecycle for the first interactive chat

1. SIS validates opt-in configuration and conversation ID.
2. Existing ChatStore appends the user message and increments its order index.
3. ConversationExecutionService builds a bounded user/assistant history window; no tool/system transcript is injected.
4. The existing ServiceContainer-resolved LLMService is invoked with Hydra-configured model, timeout and output limits.
5. On provider failure, the idempotent user message remains persisted/marked failed; no synthetic assistant response or completed turn is stored.
6. On success, ChatStore atomically appends the observed assistant response metadata and its existing ChatTurn.
7. A real authenticated SIS route invoked `ollama/qwen3`; its two-message conversation and turn were re-read through a fresh Python process.

The route is non-streaming; its async provider request supports best-effort cancellation but no durable job/restart cancellation recovery. Plain chat does not create PlanTrace; STN03 should add explicit references for actual workflow runs without making ordinary turns heavyweight. The checked-in feature/readiness flags remain false and the local account must be configured before normal users can sign in.
